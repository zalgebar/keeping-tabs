Keeping Tabs

Concept

The concept

Score pads work because they sit flat on the table and everyone can see them. Phone scorekeeping apps break that — one person holds the device, everyone else asks "wait, what am I on?"

Keeping Tabs puts the device flat in the middle of the table and treats the screen edge as the table edge. Each player gets a tab protruding from the perimeter. You drag your tab to the edge nearest where you're sitting, and it stays there for the whole game. Because the tab's text is rotated to face outward, everyone reads their own score upright without leaning across.

The gimmick is the product. Everything else in this plan is in service of making the tabs feel good.

Design principle

If a feature makes the tabs harder to read from across the table, it loses. The center of the screen is for game state; the edges belong to players.

Design principle

The app never infers the physical world. A tab moves when someone moves it, and at no other time. No sensor, rotation or orientation change is treated as intent.

Clever inference fails the same way spatial audio does: it is right often enough to be trusted, and when it is wrong the user has no model for why and no obvious way back. A scorekeeper that rearranges itself is worse than one that makes you drag a tab, because dragging always works and is always understood.

Voice

Warm and plain-spoken, with jokes used sparingly and only where they're earned. The winner of a game is crowned Edge Lord — a title, awarded once, at the moment everyone is already looking at the screen. It is not the app's word for "player": Add player is clearer than Add edge lord, and a joke repeated on every button stops being one by the second game.

Only first place gets a title. Last place gets nothing — no booby prize, no wooden spoon. A shared screen in the middle of a table is the wrong place to point at whoever already had the worst night, and a scorekeeper that mocks people is one they stop reaching for.

Edge Lord appears in exactly one place in the app: the end-of-game screen. Not as a placeholder, not as an input hint, not as a default roster name, not sprinkled through empty states. Confining it to a single moment is what keeps it funny, and it leaves every field and label in the rest of the app plainly worded for someone meeting it for the first time.

Rule

The joke is never load-bearing. Every screen has to make complete sense to someone who doesn't get the reference — a grandparent at the table, a first-time player, a screen reader. "Edge Lord" rides alongside a plain statement of who won, never instead of it: the result reads Ann wins in large type, with the title as a small badge beneath.

Mechanic

The edge-tab mechanic

Tabs live inside the screen

The screen is the whole canvas — there is no space outside it for a tab to stick into. So every tab is anchored flush against its edge and protrudes inward, rounded only on the inward-facing side, like a bookmark hanging into the page.

Each tab is a length × depth box: length runs along its edge, depth reaches into the screen. Depth is a constant — 72px — and length is what varies as edges get crowded.

This makes the implementation unusually clean. Author one tab component as a length × depth box with upright text, then place it with a single translate(…) rotate(…). The four edge transforms are constants derived once. No per-edge markup, no swapping width and height for the vertical edges, and one rotation value that serves both the box and its text.

The center is what's left over

Tabs eat real estate, so the center isn't the viewport — it's the viewport inset by the tab depth on each edge that currently holds tabs. Game state lays out inside that computed rect and reflows when a tab moves to a different edge. On a 390 × 844 phone with all four edges occupied, that leaves 278 × 732 for the round counter and End Round, which is more than enough.

Corners are reserved

Two tabs on adjoining edges would collide in the corner square, so each edge's usable span excludes one tab-depth at both ends. Nothing is ever placed in a corner, and the four corners stay visually quiet — which is also where a settings affordance can live without competing with anyone's score.

Lighting must not cost colour

The tab is lit rather than flat: a highlight along the inward lip and along the side edges, so it reads as a physical object on the table instead of a coloured fill. The obvious companion — a shadow where the tab meets the bezel — is deliberately absent.

Tested across the player palette, darkening the lower half of a tab visibly costs colour separation: green and teal begin to converge, and the olive goes muddy. Colour is one of the three player identifiers, so any treatment that mutes it works against the same requirement the animal emoji exists to satisfy. Any future finish has to leave saturation alone.

The finish is applied on an overlay, not the tab's own shadow, which the lifted state owns — otherwise picking a tab up erases its finish.

What's inside a tab

Two rows stacked across the tab's depth: emoji and name on the first, the numbers on the second. Depth is a fixed 72px and otherwise underused, so the emoji costs no length — and the round and total sit on their own row, unaffected by how far the name has had to shrink. All the length pressure falls on the name, which is the part that can afford it.

Position is stored as edge + fraction

Not x/y, and not a single scalar walking clockwise around the perimeter. Both of those reshuffle players when the device rotates or resizes. { edge: "right", fraction: 0.35 } survives any viewport change — the person on your right stays on the right.

Player identity

Every player carries three identifiers: a name, a colour, and an emoji, both assigned at random on creation. The emoji shows on the tab at every size — never introduced only once things get tight, which would force people to learn a new identifier at the worst possible moment.

The curated pool seeds the defaults and nothing else. A player may type any emoji at all, or any character, and pick any colour from the system picker. Two players may share an emoji or a colour if that is what they want, and they may choose something that renders badly on someone else's device. None of that is the app's business — it only has to guarantee a sensible starting point.

That also keeps the interface small: an emoji field and a colour swatch on each row, rather than two large grids of things we decided were acceptable.

Animals rather than people: no skin-tone modifiers to handle, no gendered defaults, and the silhouettes are more distinct. This is also what retires initials — with 16 players, colliding initials are near-certain (two Sams both read as "S"), while a fox and a whale never collide at any size.

The default pool

Hand-curated animals, not the whole Unicode block, and used only to pick starting emoji. Two filters: distinct silhouettes at 20px — 🐶🐕🦮🐩 are one shape rather than four, and 🐻🐨🐼 are three brown circles — and universal support, nothing newer than Unicode 9.0, so an older tablet at game night renders animals instead of tofu boxes.

Defaults prefer an unused animal and an unused colour, so a fresh table starts distinguishable without anyone having to think about it. Once the pool is exhausted, or once someone edits, duplicates are simply allowed.

Emoji ignore CSS color and render in their own palette, so they need a light disc behind them on the tab; a dark animal on a dark player color would otherwise disappear.

How many fit

Measured on a 390 × 844 phone in standalone mode, with safe-area insets applied and corners reserved: the short edges have 246px of usable span each, the long edges 607px. The long edges carry roughly 2.5× what the short ones do, so auto-arrange allocates players proportionally to span rather than round-robin.

Tabs on the same edge push each other rather than overlap — a one-dimensional relaxation pass, clamped inside the reserved corners. As length per tab shrinks, content drops in this order:

Tab lengthShowsReached at
≥ 140pxEmoji · full name / round · totalUp to ~12 players
100–140pxEmoji · first name / round · total13–16 players
72–100pxEmoji · first name / totalClustering only
< 72pxEmoji / totalClustering only

The bottom two tiers are mostly reachable by dragging players onto the same edge — they exist so clustering degrades gracefully. The floor is 56px; below that an edge is full and new tabs spill to the next-emptiest one.

Tabs must not fill their edge

Sizing tabs to consume the whole usable span leaves exactly zero slack, and slack is what the push mechanic runs on. With none, a neighbour can never slide out of the way — it can only snap when the sort order flips, which reads as the shove working in one direction and not the other. Tabs therefore take about 92% of the span and leave the rest free.

The dragged tab is also pinned, with everything relaxing outward from it in both directions, and the passes that resolve the ends of an edge run only when an end is actually violated. Relaxing from one end unconditionally instead lets the dragged tab be displaced by its own neighbour rather than displacing it.

Displacement is provisional until the drop

A shoved tab must not treat each frame's new spot as its home. Record continuously and the shove ratchets: a resident can be pushed along an edge without limit and can never return. Record never, and the shove is merely cosmetic — the tab springs back the moment anything re-lays out, and a rearrangement the user just made is silently lost.

The rule sits between the two: show the displacement during the drag, discard it if the mover moves away, record it on drop. Every frame re-derives the shove from each resident's original position rather than from its last shoved one, and the commit happens while the dragged tab is still pinned, so what gets stored is exactly the arrangement on screen.

Slack, the pin, and provisional commit were all found by using M1, not by reasoning about it — three separate bugs in the same mechanic, none of which were visible on paper. That is what the prototype was for.

Measured, and one caveat

Fresh auto-arrange at 16 players on 390 × 844 gives 2 top, 2 bottom, 6 left, 6 right at 110px and 102px — every tab showing emoji, first name and both numbers, with 58px of slack on the long edges.

That measurement has no safe-area insets, because desktop browsers report zero. On a notched phone in standalone the long edges lose about 93px to the island and home indicator, which at 16 players puts those tabs near 88px — one tier down, dropping the round number. Both numbers should survive to roughly 12–13 players there. Confirming this is part of the on-device pass.

Why 16 and not more

Geometry allows about 34 tabs before hitting the floor. The cap is far below that because pixels stop being the constraint first: past roughly 14 people, most of the table physically can't reach the device, and the app quietly becomes one person operating it for everyone — the exact thing it exists to fix.

No orientation default, and no prompt

The app takes whatever orientation it is given. Capacity is identical either way — the perimeter is 2(w+h) and corner reservation is a fixed eight tab-depths, so a 390 × 844 phone offers 1828px of usable edge in portrait and 1828px in landscape. The edges only swap roles.

Nor is there anything to nudge people toward. Someone picks the device up, orients it the way they want, and sets it down; asking first is a decision with no consequence placed in front of the fun. A device lying flat also has no gravity vector to sense, so iOS generally will not auto-rotate it at all — orientation is settled once, by hand, and then stays put.

Drag versus tap

These must never be confused mid-game — an accidental reposition while someone is trying to score is the worst failure mode in the app. Two independent safeguards:

  • Press-and-hold for 350ms to lift a tab, with a visible pick-up state. A tap under that threshold always means "open my panel".
  • Arrange mode — an explicit toggle in the center that locks or unlocks all tabs. Locked is the default once a game starts.

While dragging, the pointer is projected onto the nearest of the four edges: compute the perpendicular distance to each, pick the minimum, then clamp the position along that edge to a fraction.

Auto-arrange

On setup, entering N players distributes them evenly around the perimeter. Dragging to match the real table is then an adjustment, not a chore. This is the ten-second onboarding.

Scoring

The scoring model

Two display modes

  • Total only — one big number per tab.
  • Round and total — the round score small and secondary, the total large. This is the two-number tab.

Rounds are universal; categories are not

These are separate features and should not be built together. Round-plus-total works for every game and is cheap: End Round commits each player's round score into their total, archives the round, resets round scores to zero, and increments the counter. A round-by-round grid view falls out of this for free.

Named score categories — Wingspan's five columns, Scythe's coins — need per-game templates and a game definition format. That is a materially bigger feature with a much narrower payoff. It is deferred, and when it comes it should arrive as a general "custom fields" layer rather than a library of hand-written game definitions.

Two markers, matched to signal strength

A tab carries two pieces of state beyond the numbers: who's winning overall and who took the last round. They get different marks, and which mark goes where is decided by how loudly each one reads.

A star is the more visible mark and the more commonly understood one — nobody needs it explained. So it carries the more important signal: the lead. A bar is quieter and less immediately legible, but still informative once seen, which makes it right for the secondary signal. Strongest mark to the most-asked question.

They also sit on opposite edges of the tab, so one player can hold both at once without the two ever competing.

Star · in the lead

On the outer strip, the sliver flush against the screen edge that holds nothing else. "Who's winning?" is the question a table asks constantly, and the round history grid answers it badly — scanning sixteen totals at four different rotations is precisely the work this app exists to remove.

  • Respects lowest-wins, so a golf game stars the lowest total.
  • Ties star every tied player.
  • Suppressed while all totals are equal, which covers the opening round before anyone has scored.
  • Derived from current totals — nothing stored, undo free.
  • Accessible name appends "in the lead".
  • No need to clear at End Game: the leader is the winner, so the star and the Edge Lord announcement agree by construction.

Bar · won the last round

A bright rule along the tab's inward edge, the side facing the centre of the screen. The tab reads as lit rather than badged. It answers "who's hot right now", which a running total is specifically bad at showing, and it animates in at End Round — already the moment everyone is looking up.

  • Respects lowest-wins, so a golf round lights the lowest scorer.
  • Ties light every tied tab.
  • Suppressed when every round score is identical — lighting all sixteen tabs tells nobody anything.
  • Clears at End Game, so nothing distracts from the result.
  • Derived from the last entry in rounds — nothing stored, undo free.
  • Accessible name appends "won last round".

Neither costs any tab length, so both survive every compaction tier right down to emoji-plus-total.

Why the star is inline SVG

Not a letter, and not the ⭐ emoji:

  • The tab already carries an animal emoji as the player's identity. A second emoji beside it competes, and the eye can't separate who you are from how you're doing. An SVG mark reads as interface rather than identity.
  • SVG takes currentColor, so it can be tuned for contrast against any player color. Emoji paint in their own palette and would need the same light-disc workaround the animals require.
  • Identical on every platform, with no Unicode version floor to respect.

Star rather than laurel: a laurel wreath at 14px collapses into a ring of squiggles, while a star holds its silhouette at any size — which is why star shapes became the standard for ratings in the first place.

Worth watching in M3: a visible leader can encourage pile-on in games where that matters. If play testing says it makes games worse, it becomes a preference — but not before, and not by default.

The detail panel is the tab, grown

Because tabs already protrude inward, the panel doesn't need to be a separate surface sliding over the top. Tapping a tab grows it further inward — same anchor, same edge, same rotation, just more depth. One continuous animation from a 72px tab to a panel deep enough to hold controls, and closing it retracts back to a tab.

That keeps the person entering their score at their own side of the table, never reaching across or reading upside down, and it means there is no moment where the player loses track of which surface is theirs. The expanded tab holds:

  • A large adjustment pad — ±1, ±5, ±10, and a custom entry
  • That player's running history of deltas for the current game
  • Per-player undo
  • Rename and recolor

Non-negotiables

  • Global undo. Every score change is an event on a stack. Undo pops it. This gets used constantly.
  • Lowest wins toggle. One boolean. Without it the app is useless for golf, Hearts, and Barbu.
  • Autosave on every mutation. Someone will close the tab mid-game.
  • Negative scores. Plenty of games go below zero.

End of game

End Game freezes scoring and shows the final standings in the center, oriented for whoever tapped it. First place is announced plainly — Ann wins, in the largest type on the screen — with the Edge Lord title as a badge beneath it. Winner is determined by the winCondition setting, so a lowest-wins game crowns its Edge Lord correctly.

Ties produce co-Edge Lords rather than a tiebreak; the app doesn't know your house rules and shouldn't pretend to. From here the only actions are export, copy standings, rematch with the same roster and positions, or new game.

Table presence

A score change briefly swells the tab and animates the delta (+7) so the whole table sees who just scored. Cheap to build, and it's what makes the app feel like it belongs on the table rather than in someone's hand. Double-tap for +1 keeps trick-taking games fast.

QR roster transfer

  • Device A shows a QR containing the roster itself
  • Device B scans it — done
  • No keys, no relays, no network
  • Solves the stated pain at a fraction of the cost of sync
Why QR roster transfer belongs in 1.0

A QR code comfortably carries about 2KB. A ten-player roster is roughly 200 bytes. Moving player groups between devices — the actual thing that needed solving — turns out not to require any sync infrastructure at all. It works on a plane. Roughly a day of work.

The last-three-games buffer

A rolling local buffer of the last three completed games. It's the smallest thing that fixes the two real complaints — "we forgot to export" and "what did we score last time?" — and it's a fixed-length array in localStorage, so it needs nothing v1.0 doesn't already have.

Three rather than unlimited is deliberate. It stays a buffer rather than a history feature: no list to manage, no storage growing without bound, no implication that the app is an archive. The fourth game drops off silently, and export stays the way to keep something permanently.

v1.1 doesn't create this — it carries it, publishing each buffered game as a keepingtabs/game/<id> event so a new device can pull the last three down rather than starting blank.

Explicitly not in 1.0

  • Any network calls, accounts, or keys
  • Open-ended game history — the buffer stops at three, and there's no browsing, searching, or importing past that
  • Named score categories or per-game templates
  • Turn timers, dice, or anything that isn't score
v1.1

v1.1 — The sync layer

A bolt-on behind a single Sync screen. Because v1.0's local cache is already authoritative, this layer only ever reconciles — it never becomes a dependency, and the app keeps working identically with sync switched off.

Why nostr fits

  • No accounts, no email, no passwords, no backend — the app stays a static file on GitHub Pages indefinitely.
  • NIP-78 (kind 30078) is application-specific addressable data, keyed by a d tag and replaceable. "Latest roster" is exactly one event, overwritten in place. No storage scheme to invent.
  • NIP-44 self-encryption means relays hold opaque ciphertext. Player names are personal data and shouldn't sit in the clear on a stranger's relay.

Event layout

d tagHoldsShape
keepingtabs/rostersAll saved player groupsReplaceable, one event
keepingtabs/prefsDisplay mode, theme, defaultsReplaceable, one event
keepingtabs/game/<id>One completed gameOne event per game
keepingtabs/indexGame ids plus summariesReplaceable, one event

Splitting games into individual events rather than one growing history blob keeps every event far below relay size limits and makes partial sync trivial.

The game events are how v1.0's last-three-games buffer travels. v1.1 publishes each buffered game and imports them onto a new device, so a freshly paired phone arrives with the last three results already in place instead of starting blank. The buffer itself is v1.0 and works with sync switched off — v1.1 only moves it between devices.

Device transfer

The user's terminology is never nostr or nsec. In the interface it is a Sync Code. Two rules make the QR handoff safe:

  1. Generate a fresh, app-specific key. Never accept an existing nostr identity. If someone pastes in the key behind their real nostr identity and the app throws it on screen at a party, that's a genuine compromise of something that matters. Don't offer the input field at all.
  2. Encrypt the QR payload with ncryptsec (NIP-49) under a short PIN. Device A shows the code and a four-digit number; you say the number out loud to whoever's holding device B. A photograph taken across the table is useless on its own.

Conflict and clock handling

  • Last-write-wins is acceptable — this is a shared device on a table, not a collaborative document.
  • Replaceable events resolve by created_at, so a device with a wrong clock can publish a "future" event that permanently shadows good data. Always publish with created_at greater than the newest seen, and keep a monotonic rev counter inside the encrypted payload that is trusted over the timestamp.
  • Writes go to an outbox while offline and flush on reconnect.
  • Publish to five or six relays in parallel; the relay list is user-editable.
Framing, honestly

Public relays make no durability promise — they prune, go down, and disappear. This is convenience sync, not durable backup. File export stays in the product as the thing you do once a year. And there is no recovery path: lose every device, lose everything. That's the real price of having no accounts, and the Sync screen should say so plainly rather than let people discover it later.

What this quietly unlocks later

If every player's phone subscribes to the same key, everyone watches the score live on their own device. That's a different app and a scope explosion — but it's a door this architecture leaves open rather than closes.

Data

Data model

One versioned blob in localStorage under keepingtabs.state. The version field exists so v1.1 can migrate without guessing.

{
  version: 1,

  prefs: {
    scoreMode:     "total" | "round-and-total",
    winCondition:  "high"  | "low",
    wakeLock:      true,
    theme:         "auto" | "light" | "dark"
  },
  rosters: [
    { id, name: "Thursday Crew",
      players: [ { name, color, emoji } ] }
  ],

  recentGames: [ /* last 3 completed, newest first */ ],
  game: {
    id, startedAt, round: 3,
    players: [
      { id, name, color, emoji: "🦊",  // unique within a game
        edge: "left", fraction: 0.35,   // perimeter position
        total: 42, roundScore: 7 }
    ],
    rounds: [                            // committed rounds
      { n: 1, scores: { playerId: 12 } }
    ],
    log: [                               // the undo stack
      { id, ts, type: "delta" | "commit-round" | "rename",
        playerId, value, roundNo }
    ]
  }
}

The log is the single source of truth for undo. Totals are derived state — if they ever disagree with the log, the log wins and totals get recomputed.

Tech

Technical shape

v1.0

  • Single-file vanilla HTML/CSS/JS. No framework, no build step, no dependency rot. Push to gh-pages and it's live.
  • Pointer Events throughout — never separate mouse and touch paths. touch-action: none on tabs.
  • CSS transform: rotate() for tab orientation; layout in JS from the edge/fraction model.
  • Service worker with a cache-first strategy over a tiny, fully-versioned asset list.

The install prompt

One row on the Sync & Export screen — the export screen in v1.0, before sync exists. No banner, no interstitial, no trigger logic, and no dismissal flag, because there is nothing to dismiss.

That screen is the right and only place because someone standing there is already asking how do I not lose this?, and installing is a real answer to it. A prompt that answers the question the user is currently asking is information; the same words anywhere else are marketing. It's reached naturally from End Game, which is where export already lives, so the option doesn't have to chase anyone to be found.

The row hides when the app is already installed — gate on display-mode: standalone and, on iOS, navigator.standalone. An installed app offering to install itself is the most common PWA bug there is.

On Chromium, beforeinstallprompt gives a one-tap install; the event is single-use, so it's re-captured on each fire rather than stashed once. On iOS no such API exists, so the row shows the Add to Home Screen steps instead.

Build

Build order

M1–M7 are build milestones, not releases. Only two things ship: v1.0 at M5 and v1.1 at M7. The letters keep the two schemes from colliding — numbering the milestones v0.1–v0.7 would put v0.6 and v0.7 after v1.0, which reads like the version going backwards.

M1 exists to answer one question before anything else gets built: does dragging a tab around the perimeter actually feel good? If it doesn't, the rest of the plan is wrong.

M1
Perimeter prototype
Drag, edge projection, inward-protruding tabs, rotation, packing at 16 players, safe-area insets. Throwaway code, no persistence. Test on a real phone on a real table — that's the only way to know whether the feel is right.
M2
Scoring core
Players, the event log, adjustment pad, global undo, localStorage autosave.
M3
Rounds and the detail panel
Edge-anchored rotated panel, End Round, round history grid, lowest-wins, leader star and last-round bar.
M4
Setup, rosters, QR transfer
Player entry, color assignment, saved rosters, QR show and scan.
M5
Table hardening
PWA, service worker, wake lock, export, last-three-games buffer, orientation handling. v1.0 ships here.
M6
Sync foundation
Key generation, NIP-44 encryption, NIP-78 publish and fetch, relay pool, offline outbox.
M7
Sync screen and device handoff
PIN-encrypted QR, reconciliation, conflict guards, importing the recent-games buffer onto a new device, plain-language status. v1.1 ships here.
